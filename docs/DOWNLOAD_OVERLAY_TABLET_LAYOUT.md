# 下载浮层的布局契约（重做设计）

> 本文是**动手之前**的设计，不是既成事实的记录。实现完成后把「现状」一节删掉，
> 并把守卫项落成 `tools/check-download-ui-contract.py` 里的断言。
>
> 相关：[DOWNLOAD_TRANSACTIONAL_CHUNKS.md](DOWNLOAD_TRANSACTIONAL_CHUNKS.md) §UI 可达性
> 记着宽度模型的三代演进与各自的失败形态，那些坑不要再踩一遍。

## 一、为什么要重做，而不是继续打补丁

浮层是**纯程序化 Java 视图**，没有 XML 布局、没有资源限定符，因此也就没有
「换个屏幕尺寸自动换一套布局」的机制。整个补丁层里没有一处平板、横屏或
`smallestScreenWidthDp` 分支，也不消费任何 `WindowInsets`。

它在手机上能用，是因为所有尺寸都是照着一部手机调出来的常数。平板上的问题不是
「某个数字调歪了」，而是**没有任何一处代码知道屏幕可能变大**。逐条改数字治不好，
所以重做布局系统。

现状里最刺眼的一条，也是重做的起点：**字号被拿来当宽度用**。推荐字号按 dp 宽度
线性给（720dp 为基准，上限 125%），而字号大于 100% 时内容宽度被设成
`视口 × 字号百分比`。于是典型 1200dp 宽的平板拿到 125%，内容比视口宽出四分之一，
右边那 20% 被推出屏幕——而每一行的「重下 / 确认」按钮、文字进度、总进度条的
右端恰好都在那 20% 里。手机上算出来是 95%，走的是 `MATCH_PARENT`，永远碰不到
这条路。

## 二、三条硬判据

新布局的每一个决定都要能回答这三条中的一条，否则就是在凭感觉调数字。

**判据一：内容永不超出视口。** 不允许出现横向滚动。字号只改字号，不改任何
容器的宽度。视口放不下的时候，缩的是内容（换行、堆叠、省略），不是把视口撑破。

> 这一条直接废掉现状里 `want = viewport × scalePct / 100` 那一行。横向滚动条随之
> 永久消失——它本来就是「内容比视口宽」这个错误的症状，不是功能。

**判据二：可触区域永远在可见区域内。** 任何时候，每一行的操作按钮都必须在不滚动
的情况下够得到。这是浮层的功能底线：玩家看得见进度却点不到「重下」，等于没有。

**判据三：屏幕尺寸只影响布局，不影响语义。** 同一份下载状态，在手机和平板上必须
表达同一件事：同样的行数、同样的措辞、同样的按钮。平板不是「手机的放大版」，也
不是「功能更多的版本」。

## 三、尺寸档位

按 `Configuration.smallestScreenWidthDp` 分三档，断点取业界通用值，不自造：

| 档位 | 判据 | 典型设备 |
|---|---|---|
| `COMPACT` | < 600dp | 手机竖屏、平板小分屏 |
| `MEDIUM` | 600–839dp | 小平板、折叠屏展开、平板半屏 |
| `EXPANDED` | ≥ 840dp | 平板横屏、桌面模式 |

档位在 `buildOverlay` 里算一次，作为参数往下传；**不允许各处自己再去读
`DisplayMetrics`**。现状里那个从 `widthPixels` 算出来又没人读的
`contentBaseWidthPx` 就是反面例子——一个散落的尺寸来源迟早和别处对不上。

> 用 `smallestScreenWidthDp` 而不是当前宽度：它描述的是**设备**有多大，横竖屏
> 切换不变。当前窗口有多宽是另一个量，见下一节。

### 每档的布局

| | `COMPACT` | `MEDIUM` | `EXPANDED` |
|---|---|---|---|
| 主区排布 | 单列纵向堆叠 | 两列 40 / 60 | 两列 32 / 68 |
| 署名区 | 收进可折叠区，默认收起 | 常驻左列 | 常驻左列 |
| 面板最大宽度 | 无（占满） | 无（占满） | 1100dp，超出部分左右留白居中 |
| 字号基准 | 100% | 100% | 105% |
| 面板外边距 | 12dp | 20dp | 32dp |

两处需要解释：

**为什么 `EXPANDED` 要设最大宽度。** 13 寸平板上一行文字横跨整个屏幕，眼睛要
从最左扫到最右才读完一行，反而比手机难读。给面板设上限、两侧留白，是让行长回到
可读区间，不是为了好看。

**为什么 `EXPANDED` 的字号是 105% 而不是 125%。** 平板离眼睛更远，字确实该大一点，
但**大的是字，不是布局**。105% 是在不触发任何换行/截断变化的前提下能给的余量；
再往上就该调的是行高与间距，不是继续放大字号。现状那个 125% 的由来是想用字号
去解决「界面在大屏上显得小」，而它真正造成的是内容溢出。

## 四、窗口宽度与档位是两件事

档位来自设备，**当前可用宽度**来自窗口，两者在分屏、折叠、自由窗口下会分道扬镳。
一部 `EXPANDED` 平板可以只给浮层一个 400dp 宽的分屏窗口。

所以布局决策是**两级**的：

1. 档位决定「打算怎么排」（两列还是堆叠、要不要留白、字号基准）；
2. 当前可用宽度决定「排不排得下」——可用宽度 < 600dp 时，无论档位如何，
   一律降级为单列纵向堆叠。

第二级是保险丝，不是主逻辑。没有它，平板分屏就会拿着 `EXPANDED` 的两列方案去挤
一个手机宽度的窗口。

窗口宽度的唯一来源是**已测量的视口**（现状 `viewportPx` 的做法是对的，保留），
并且要在 `onLayoutChange` 里跟随变化重算——**包括重算字号基准**。现状只重算列宽
不重算字号，于是分屏启动时按整屏宽算出的字号会一直用到关页面。

## 五、系统留白（inset）

浮层直接挂在 `decorView` 上，覆盖状态栏、导航栏、刘海与手势区。现状完全不处理，
后果在平板上尤其明显：底部署名条压在 Android 12L 以上的平板任务栏底下；横屏时
刘海在左右长边，正好压住顶部那排胶囊。

做法：根视图消费 `systemBars` 与 `displayCutout` 的并集，作为 padding 加在最外层。

```
API ≥ 23  →  getRootWindowInsets()，取 systemWindowInsets ∪ displayCutout
API 21/22 →  全给 0
```

21/22 给 0 是有依据的：那两个版本既没有刘海也没有手势条，状态栏区域由
`fitsSystemWindows` 之外的老机制处理，浮层本来就是全屏覆盖。**不要**为此引入
AndroidX（铁律 3：classpath 只有 android.jar + OkHttp）。

## 六、弹窗

现状有六个弹窗写死 330 / 360dp 宽，两个高度上限按**整屏**高度算。平板上是巨大
暗色层中间一张邮票；平板分屏里反而会溢出窗口。

统一规则：

- 宽度 = `min(560dp, 可用宽度 − 2×32dp)`，且不小于 280dp；
- 高度上限按**窗口**高度算，不是屏幕高度；
- 一律走同一个函数，不允许某个弹窗自己写常数。

高度那条的现状值得单独点名：用 `heightPixels × 0.8` 当上限，在多窗口下会算出比
窗口还高的值，于是「离线导入」对话框底部的关闭按钮又一次跑到窗口外——而那个
上限当初正是为了防这件事加的。

## 七、要落成守卫的条目

这个仓库的规矩是：**不可执行的约定等于没有**（铁律 4）。下面每一条都要变成
`tools/check-download-ui-contract.py` 里的断言，否则下一个人照旧会写回去。

| 断言 | 防的是什么 |
|---|---|
| 布局代码里不出现「内容宽度 = 视口 × 系数」这类写法 | 判据一被悄悄退回 |
| 三个断点常量存在且为 600 / 840 | 有人随手改成「我这台平板正好的那个值」 |
| 除档位计算处外，不出现 `widthPixels` / `heightPixels` | 散落的尺寸来源 |
| 所有弹窗宽度都经过统一函数 | 又一个写死 330dp 的弹窗 |
| 根视图有 inset 消费，且带 `SDK_INT` 守卫 | inset 被删掉，或在 21 上崩 |
| 字号变化不触碰任何容器宽度 | 判据一的另一半 |

## 八、怎么验证

浮层是 Android 视图，本机没法像网页那样跑起来看。分两层验证：

**布局决策纯函数化 + JVM 单测。** 把「给定档位、可用宽度、系统字号 → 列宽、
是否堆叠、面板宽度、字号」抽成不依赖 `Context` 的纯函数，用 `tools/*Test.java`
覆盖各档位与边界（599/600/839/840dp、分屏、系统字号 1.3）。现有
`UiAssistStateTest` 已经是这个套路，照着扩。

**模拟器截图。** 本机有 Android SDK 与模拟器，起两个 AVD 配置（平板横屏
1920×1200、平板分屏半宽）装包截图，人眼过一遍。这一步抓的是纯函数测不到的东西：
文字换行、图标比例、留白观感。

> 两层都不能省。单测保证「算出来的数对」，截图保证「看起来是对的」——现状那些
> 问题（署名区压在任务栏下、13 寸屏上一行文字横跨全屏）单测一个都发现不了。
