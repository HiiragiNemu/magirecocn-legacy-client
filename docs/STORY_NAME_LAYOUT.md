# 原国服姓名布局兼容

> 当前实现以文末 1.0.202 的「基线与字身坐标适配」为准。1.0.199/200/201 是历史步骤；节点坐标、基线相等或钩子命中，都不能单独作为金条内实际留白正确的证明。最终发布状态另附构建、实播与分发回执。

## 范围

1.0.199 仅对普通 StoryMessage 的姓名局部位置补齐国服差异。姓名仍是原消息包裹节点的子节点；保留原引擎的安全区域、屏幕比例、左右锚点、空名与喊话处理。没有替换字体、字号、正文布局、气泡图片或任何存档与下载协议。

## 原生证据

对原国服 2.2.1 与归档基础引擎的 AArch64 副本，分别核对 StoryMessageUnit 的创建、姓名更新、正文启动和旧消息回收函数。原国服 createMessageArea 位于 0xA05AE8，归档基础引擎同函数位于 0xCE87C0。三种姓名的父节点内坐标为：

| 分支 | X | 国服 Y | 归档基础引擎 Y | 锚点 |
| --- | ---: | ---: | ---: | --- |
| 左 | -215 | 63 | 57 | (0, 0.5) |
| 中 | -55 | 63 | 57 | (0, 0.5) |
| 右 | 215 | 63 | 57 | (1, 0.5) |

这是局部坐标差异，不是固定屏幕像素差异。中间姓名按左边缘定位，不能根据姓名字数再次居中。外层适配并不属于本次修正，不能用替换整个旧函数的方式丢掉后续引擎的安全区支持。

## 限定修正与失败保守处理

在原 createMessageArea 调用期间使用线程局部作用域，借用已有字符串 TTF 创建入口记录原引擎的两个 Label。只有构造顺序、两个原字号、名字节点、三种原坐标和锚点全部符合已核实结构时，才调用原 Node 公共 API 将局部 Y 从 57 改成 63。没有修改游戏库机器码、硬编码对象内存偏移或全局 Node 位置钩子。

字号仅用于识别原节点，不作写入。已有字体调试开关关闭构造钩子、符号不可用、构造形状变化、空指针、未知位置或已经处于 63 时，全部保持原样。作用域支持嵌套并在退出时恢复；不保存超出调用期的 Label 指针。

每个进程每种位置最多记录一条不包含姓名内容的命中日志，便于安装验收确认不是只编译了未命中的代码。

## 回归与发布边界

`tools/StoryNameLayoutTest.cpp` 使用生产同一头文件，覆盖左中右、未知形状、额外构造、无效函数、已修正节点和嵌套作用域。既有手动 APK 工作流在双架构编译之前执行该测试。工作流触发方式和发布链保持不变。

本机语法/双架构构建只是前置验证，不能代替完整 APK 构建、实际安装命中、原签名兼容和升级后场景验证。应先构建校验包，在通过上述检查后才发布。版本旁注、实际 APK 和玩家更新入口必须一致；本文件不作为发布已完成的凭证。

## 正文隔离复核

姓名修正不包含正文策略迁移。当前基础引擎的正文构造保留字号27、上锚点(0,1)、TOP对齐、38行距和410最大行宽；本补丁只记录正文构造以识别随后姓名，不对正文调用位置、锚点、大小或对齐 setter。原国服固定高度及CENTER正文不在本次客户端改动范围。

发布采用现有的固定主线源码构建及同产物发布流程，不能把本机替换补丁库的校验包直接分发；完整产物必须比对上一正式版本的资源、字体、原游戏库、身份和签名后才提升在线客户端版本。脚本及剧情热更新版本不由本改动重置。


## 1.0.200：补齐姓名节点尺寸，不改正文

1.0.199 只修正局部纵坐标，遗漏了原国服姓名字号 20 与基础引擎 16 的区别。行高两者均为 25。1.0.200 在同一已核实创建作用域内，连同姓名字号一起修正；仍不触碰正文、字体文件、消息父节点、安全区域或缩放。

只有两个 Label 的构造顺序、原字号、局部坐标、锚点、渲染字号和行高全部匹配时才写入。通过公开 getTTFConfig/setTTFConfig 接口重新生成同字体、20 号的姓名标签，再恢复原有 25 行高和国服局部 Y=63。不能调用 setSystemFontSize，因为它会改变标签的字体渲染类型。

配置 ABI 已分别核对 64 位与 32 位基础引擎。修改的是公开配置值，不是 Label 对象内存偏移。原字体路径另行持有到同步 setter 及失败恢复完成，避免字体加载失败时原节点重置导致借用的路径失效。未知结构、不完整 API 或异常仍保持保守处理，不替换字体。

同源主机测试验证三个姓名槽位、字号/行高/坐标守卫、重复应用、额外构造、失败 setter、嵌套作用域以及配置除字号外逐字节不变；双架构 Release 编译通过。实际目标剧情的本机校验包已取得左、右姓名 16→20 / 57→63 命中及正文不变截图。此记录不代替最终完整 APK 的逐文件对比、签名核验和 APP 内更新验收；正式发布结果须另附实际构建和分发回执。

## 1.0.201：保留字库时的基线映射（2026-10-02）

用户提供的是医院内中间气泡的「彩羽」。实读 MuMu 设备3（ADB 16480）确认已安装正式 1.0.200，APK SHA-256 为 `7d28cf58feaad24b1b24de347327f852f2c7f31361472e9bbcb22abc4253a879`，中间槽确有命中。不能将该问题归因于未升级，也不能用左右槽的旧截图代替中间槽验证。

前两版遗漏的是姓名的文字基线转换，不是字体文件需要再替换。原国服 `TTDaYuanGB3.ttf` 的 hhea ascender/unitsPerEm 为 2007/2048；保留字库为 850/1000。对实际文件独立调用 FreeType，在 20 号下分别得到上升度20和17。原国服与当前引擎的 FontAtlas/Label 排版均将上升度参与字形 Y。当前客户端现场读取到姓名字体20、行框25、锚点(0,0.5)、父位置(512,115)；「彩羽」两字的字形中心Y为14.5，而行框中心为12.5。复制节点Y并不能复制可见文字的位置。

对已经识别的单行姓名，原生基线公式为 `nodeY + lineHeight/(2*contentScale) - rasterAscender/contentScale`。原国服的基线为 `63 + 25/2 - 20 = 55.5`；1.0.200 保留字库却直接使用63，实际为58.5。修复从原生字体公共接口读取当前上升度，将姓名节点映射为 `63 + (currentAscender - ceil(20*scale*2007/2048))/scale`；本机scale=1时结果为60。60是这个字库/比例下的计算结果，不是照截图写死的新偏移。

比例来自该作用域内已强制排版的单行TTF姓名行框，不使用屏幕像素比、私有Director偏移或按姓名逐字光学居中。当前基础引擎 `FontFreeType::create` 会 autorelease；补丁不手动release也不保存字体对象，只缓存同一路径/比例的数值。新增度量API缺失、空名、多行、无效尺寸或异常时保留1.0.200行为；原有构造顺序、27/16字号、位置、锚点等守卫不放宽。正文、字库文件、行高、左右锚点、父节点、安全区和网页均不修改。

`StoryNameLayoutTest.cpp` 在原守卫外增加基线、不同栅格比例、原字库无需偏移、非有限/异常度量及保守回退反例。`StoryNameBaselineTest.cpp` 可直接针对旧生产头文件运行：三个槽位在1.0.200全部失败，在新实现全部通过；断言的是同一原生基线，而非只看setter是否被调用。本机候选实际运行已记录 `rasterScale=1, ascender=17, mappedY=60`，并命中左、中、右三个槽位。最终CI产物、完整APK差异和分发结果以该次发布回执为准，本说明不冒充发布已完成。


## 1.0.202：基线与字身坐标适配（2026-10-03）

### 实证、兼容映射及其边界

原 CN 与保留引擎的 FontAtlas / getGlyphBitmap / Label 排版链均用栅格上升度与字形 bearing 放置字形；setName 只保存姓名字符串，未发现它把修正后节点重置回旧 Y。原 CN 姓名固定局部坐标63、字号20、行高25以及左右中三个锚点继续作为基准。

201 只对齐拉丁基线。实际两个 CJK 字库的 OS/2 sTypoAscender / sTypoDescender / unitsPerEm 分别为 `1599/-449/2048` 与 `850/-150/1000`，各自字身框高度均为一 em，但中心相对基线不同。保留字库的字身中心比原 CN 高 `(0.35 - 1150/4096) * 20 = 1.384765625` 个局部单位。因此本兼容层在已有基线映射上再映射字身框的中心，不根据“彩羽”等个别名字测量后逐名偏移。当前受测 scale=1 的计算结果为 `58.615234375`，不是写死屏幕像素偏移。

这里的 OS/2 中心映射是为保留不同字库而实现的兼容适配，**不是声称原国服原函数直接读取 OS/2 中点**。OpenType 对 CJK 字体的 sTypoAscender/Descender 说明了字身框上下界的含义：<https://learn.microsoft.com/en-us/typography/opentype/otspec190/os2>。字体 bearing 与基线的区别见 FreeType 官方 glyph metrics 说明：<https://freetype.org/freetype2/docs/tutorial/step2.html>。是否解决当前残差仍须实际画面验证，不能只靠该公式的单元测试。

只有原姓名创建守卫全部成立，且字体路径为三个冻结圆体别名之一、原生 getFontFamily 返回 `Magius Round Symbols`、栅格上升度匹配已核定度量时采用该适配。当前字库字节由原有 font195 产物检查固定。未知字体、缺少新增可选 API 或度量不符均保留 201 基线行为。没有额外下载或运行期全文件哈希，没有新字体对象常驻，不按每个姓名创建专门图集。仅借用现有字体对象的公开 getFontFamily/getFontAscender 结果，依旧只缓存数值。

### 候选实播与测试

新增 `StoryNameBodyTest.cpp` 的83项断言覆盖九种栅格比例、原字体不偏移、未知配置保守回退、左右中三个原 Capture 分支、重复调用不累计以及正文参数不变。既有 StoryNameLayoutTest、StoryNameBaselineTest 均仍通过；两个 ABI 的正常 Release 库构建成功。三个测试已接入既有原生构建，个人 main 手动构建也加入同样检查，不以隐藏测试替代实际入口。

本机候选以已验收的完整201为基础，仅替换两份自有 SO。对比证明其余包内内容一致，证书不变。同签名覆盖安装设备3后实际重播101201：中心“彩羽”、左“彩羽”、右拉丁玩家名、用户医院原句以及两行正文均实际显示；记录到三个位置的映射 Y=58.6152。中心同一句截图在相同3840×2160输出下，金条边界均1454..1549；避开气泡尾部后的“羽”字核心像素在195/210阈值下由1465..1527/1528变为1470..1532/1533，上下留白约16与16/17，而不是原先约11与21/22。数据来自未改动字形的原生截图，仅作为这组样本验收，不推广为所有设备逐像素相同。
