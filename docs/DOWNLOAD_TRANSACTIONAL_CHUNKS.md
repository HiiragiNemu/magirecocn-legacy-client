# 基础资源包事务分块下载

## 问题背景

`cn_base_03.zip` 约 1.4 GB，16 MiB 清单对应 85 个校验块。旧实现把“校验块数”直接当成线程数，因此会同时建立 85 个 Range 连接；同时，字节先写入 `.cpart` 并推进 `done`，到块尾才比较 MD5。块校验失败后，坏字节和“已完成”进度可能一起留在断点里。

旧 v4 断点还用 `ceil(total / chunks)` 重新估算块长，而实际块长来自清单。03 的 85 块并不能整除总长，因此完整 16 MiB 块会被误判为进度越界，导致已下载内容被反复作废。

## v5 状态模型

有有效清单时：

1. 校验块数量只描述完整性边界，网络 worker 固定上限为 8。
2. 每块先写独立临时文件，严格核对 HTTP 206、`Content-Range` 起点、终点、总长和响应长度。
3. MD5 通过后才把该块写入主 `.cpart`，同步落盘，再把块标记为 verified。
4. 元数据保存完整清单指纹；同大小但内容不同的清单不能复用旧块。CDN 的 URL/ETag 不是已验证块的身份，节点切换或 ETag 重签不会让可信进度归零。
5. 事务块始终整块请求并由 manifest MD5 认证，不发送 `If-Range`；内容真的变化会在提交前被哈希拒绝，而不会因 ETag 波动被降成 HTTP 200。
6. 单块失败时按健康镜像列表局部重试；已验证块不回退。
7. 没有清单时保留单镜像分段续传，但断点只允许在同一完整 URL 上复用，不再跨镜像拼接未经认证的字节。
8. 无清单兼容路径仍严格核对 206 的声明区间；若中间设备在准确响应头之后额外多写少量正文，只消费请求范围并丢弃尾部。

`manifest.json` 每次请求带 cache-busting 参数和 no-cache 头，并轮换起始镜像。某条镜像的清单缺少目标文件时继续查下一条，避免旧 CDN 缓存让客户端静默关闭校验。

## UI 可达性与单包重下载

旧版“字 / ↔”把控制面板挂在 Activity 的 `decorView`，并通过 `translationX/Y` 平移整个浮层；因此控件可能在资源页关闭后仍覆盖游戏，且平移窗口并不是查看被裁文本的正确模型。该实现已废弃。

当前实现遵守以下边界：

- 所有辅助控件都嵌在下载浮层内，浮层关闭即一起销毁，不进入游戏主界面；
- 中央左右两列位于固定视口中；文件区右侧显示常驻长纵向滚动条，中央视口底部显示常驻长横向滚动条；背景、顶部胶囊、底部署名和游戏画面不参与滚动；
- 顶部 `Aa` 胶囊只缩放中央内容，范围为 75%–150%。字号放大后通过两条滚动条查看超出部分，绝不使用整屏 `translationX/Y`；
- 顶部原胶囊行增加“停留本页”，启用后不受 120 秒上限影响，点击“进入游戏”才释放；显示设置、确认框或日志等模态操作期间也不会自动收页；
- 手动打开序章询问时，选择“否”只保存“正常进入游戏”并继续停留；只有选择“是”才进入必要的安全重启流程；
- 下载浮层内**不再**提供单包“重下”胶囊，也**不再**提供左右分界线拖动（2026-08-13 按维护者要求整体撤回）。两者的判据已在 `check-download-ui-contract.py` 里反向钉住：谁再加回来 CI 当场红。单包重下的**能力**并未删除——红色“重试”与调试悬浮窗的资源页仍然走 `CNManualRedownload` 那条通道，去掉的只是浮层上那颗胶囊与那条可拖的分界线。

### 任意 ZIP 并发重下载事务

任意一项都可以独立强制重下，不再要求另外 14 个 marker 或总完成标记有效：

1. 不同 ZIP 最多三个任务并行；同一文件去重。下载连接由全局公平信号量限制为合计 8 条，不能因三个文件同时重下膨胀成 24 条 Range；
2. 基础包旧 marker 在下载、校验和解压期间始终保留。新包完整安装成功后才覆盖 marker；下载或校验失败不会触碰活动树，解压阶段继续使用现有串行提交；
3. 下载可以并行，但基础包解压与 scenario/js 事务应用共用一个提交锁，活动资源树永远串行修改；
4. scenario/js 不读取基础包 `manifest.json`。本轮 `version_*.json` 的 version、size、整包 MD5 是唯一身份；每条镜像完工即整包校验，缓存旧包或同尺寸异内容会被拒绝并换线；
5. 热更新红色“重试”直接进入热更新重下载通道；首次安装器仍运行时，红色重试继续交还其原有队列；
6. 基础包成功重下后，“进入游戏”执行一次安全重启；纯热更新成功事务应用后可直接继续；有任何任务未完成时按钮不会强行离页；
7. 升级时若发现旧版 `manual-redownload.request`，先恢复被撤走的 marker；全部 marker 有效时补回总完成标记，然后终止旧式重启事务。

### 动态热更新与静态分块的边界

`cn_base_03.zip` 等静态包继续使用固定块哈希事务；`cn_scenario_update.zip` 与 `cn_js_update.zip` 是动态对象，可能出现同尺寸不同内容。动态包使用稳定的 `version-size-md5` 查询身份隔离 CDN 缓存，Range 只负责传输与断点，可信提交由整包 MD5 决定。其可见进度按收到的字节即时增长，不再等完整 16 MiB 块通过后才从 0 MB 跳动。

这条边界对**所有**取这两包的路径成立，不只是热更新那一轮：

- 热更新轮（`CNHotUpdateCheck` → `CNHotUpdate`）：按 `version_*.json` 下载并校验；
- 离线导入（`CNOfflineImport`）：直接拒收这两包，只管 13 个基础包；
- **首次安装器**（`CNDownloaderFix.fetchArchive`）：这两包被排在下载队列最前，走的仍是基础包那条路。它同样**不读**基础包 `manifest.json`，下载完工后按 `version_*.json` 的 size + 整包 MD5 核对（`verifyHotIdentity`）；版本 json 取不到时只做 ZIP 结构预检并放行，交由随后的热更新轮按版本号再核对——不因一个几十字节的冷 json 超时把整个安装卡死。

`manifest.json` 只在基础包整批出包时重算，热更两包却由热更流水线单独重发。二者脱节时清单里的块指纹指向上一版内容，而 `size` 常常不变（同结构 ZIP 重打包尺寸一致），于是 §v5 状态模型第 4 条那道「同大小但内容不同的清单不能复用」的闸<b>照样放行</b>，随后**每一块**都校验失败，四条线路轮完只剩红条重试。

> 2026-08-13 真机：`cn_scenario_update.zip` 的块 0 在 edge / esa / gh-proxy v4 / gh-proxy 四条线路上得到同一个 `bb4e7df4…`，而清单期望 `acb43c47…`。四个镜像众口一词说明文件没坏，是清单旧了；同日核对 `cn_js_update.zip` 的整包 MD5 与 `version_js.json` 完全一致，而清单里那一块同样对不上。

### 空间不足与线路故障的分界（2026-08-13）

写 `.cpart` 或解压时的 ENOSPC 抛的是普通 `IOException`，与超时、断流、坏块走同一个 catch。不区分的后果有三层：无辜线路被 `reportFailure` 记一次失败（线上 `switch_after_failures=1`，一次就进 60 秒冷却）；四次重试逐条线路轮过去把整个重试窗口白烧掉；玩家最终看到红条加四个都不解决问题的选项（重试 / 备用引擎 / 单线程 / 离线包），只会一直点重试。

因此：

1. `CNDiskSpace.isOutOfSpace` 按文本认 errno（`ErrnoException` 的常量在编译 classpath 上够不着），并遍历整条 cause 链——解压那条路是 `InstallIOException("Cannot write extraction temp: …", ErrnoException)`，包了两层；
2. 预检放在**知道大小的那一刻**：探针给出 `probe.total` 时（扣掉已有断点），以及解压前由 zip 目录累加出 `totalBytes` 时（扣掉已解压部分）。等写满再报，等于白下一个多小时；
3. 判定为空间不足时**不** `reportFailure`、**不**再重试，直接把还差多少告诉玩家。断点与已解压内容一律保留，腾出空间后重试是接着装；
4. 取不到可用空间（`getUsableSpace()` 失败）时一律**放行**——宁可照旧在写的时候失败，也不能因为读不到一个数字就把玩家挡在门外。

5. 预检要按**安装峰值**而不是下载量。峰值是 ZIP + 解压后——ZIP 要留到解压成功才删（进程被杀时好接着装）。两者比例各包差得很远，实测（2026-08-13，读线上中央目录）：

| 包 | ZIP | 解压后 | 膨胀 | 安装峰值 |
|---|---|---|---|---|
| `cn_base_03.zip` | 1.32 GiB | 2.79 GiB | **2.11x** | **4.11 GiB** |
| `cn_voice_01.zip` | 1.85 GiB | 2.15 GiB | 1.16x | 4.00 GiB |
| `movie.zip` | 1.33 GiB | 1.35 GiB | 1.02x | 2.67 GiB |
| `cn_base_02.zip` | 0.89 GiB | 0.94 GiB | 1.06x | 1.83 GiB |

`cn_base_03.zip` 是**唯一**真正会膨胀的包，也因此拥有 15 个包里最高的安装峰值。而进度条上写的是 1.3 GB：玩家按这个数清理空间，然后在解压阶段翻车。这解释了「其他包都下完了，就 03 下不下来」——03 早先失败一次后被安装器排到最后，那时磁盘已被前面十几个包填满，4.11 GiB 再也腾不出来。

解压后的大小在下载前就能知道：ZIP 的中央目录在文件末尾，每条记录都写着该条目的未压缩长度，两次 Range 请求即可（03 的中央目录 1.7 MB）。花两兆搞清楚要不要下 1.3 GB。算不出来时返回 `UNKNOWN` 并放行——它是提前量，不是关卡。

### 备用引擎（aria2）不是平行宇宙（2026-08-13）

线上 `config.json` 里 `force_aria2: true`，也就是说 **aria2c 是默认路径**：每个玩家的每个文件都先走它，失败才回退主引擎。而它此前绕开了主引擎那侧的全部验收与策略：

| | 主引擎 | aria2（修复前） |
|---|---|---|
| 内容认证 | 逐块 MD5 对 `manifest.json` | 仅 ZIP 结构预检 + 「至少有一个条目」 |
| 热更两包身份 | `version_*.json` 的 size + 整包 MD5 | 无 |
| 空间预检 | 下载前按安装峰值、解压前按 `totalBytes` | 无 |
| 单线程模式 | `CNDownloadMode.cap()` 管四处并发 | 硬编码 16 连接 |
| 换线 | `CNMirrors.pick(attempt)` 逐轮换 | 固定 `pick(1)`，三次全钉在同一条 |
| 解压 | `CNArchiveInstallTx.extract`（断点续解压 + 逐条目 size/CRC） | `extractChecked` |

这直接决定了排查方式：**只盯主引擎的日志，看到的不是玩家实际走的那条路**。2026-08-13 那轮下载问题排查之所以久久收敛不了，根因就在这里。

现已按下述口径并线（判据在 `check-download-ui-contract.py` 里钉住）：

- **换线接完整机制**，不是简化版：逐轮 `CNMirrors.pick(attempt)`，成败都回报健康表（失败记冷却、成功清计数），尝试次数与主引擎对齐好让线路表轮得完。中途换线不再打断玩家——轮完所有线路才弹一次询问框（原先每失败一次问一遍，三条线路问三遍）；
- **连接数**过 `CNDownloadMode.cap(16)`，玩家选的单线程在这条路上同样算数；
- **额外内容校验一律旁路**：不套基础包 manifest 的块指纹，也不做热更两包的 version json size/MD5 比对。判据是 ZIP 自带的完整性——没下全的包结构不合法，逐条目 size/CRC 也会在解压时把它拦下来。这条**拦得住「没下全 / 传坏了」，拦不住「下全了但是旧的」**：CDN 上一份结构完好的过期副本能一路通过，只能靠随后的热更新轮按版本号发现并补下；
- **解压仍走** `CNArchiveInstallTx.extract`——它给的是空间预检与断点续解压，不是内容校验，去掉只会让 03 那类大包白解压半天再翻车；
- **空间不足**在这条路上也走 `reportNoSpace` 并直接返回，不当「引擎失败」去问玩家：换引擎、换线路都不会让磁盘长出来。

> 需要临时回到纯主引擎时，把云端 `settings.force_aria2` 置 false 即可，不用发版。

## 回归合同

`ChunkHashIntegrationTest` 必须覆盖：

- 测试文件必须真实形成 85 个、且最后一块非整除的校验块；
- 即使调用方请求 85 个 worker，实测同时活跃连接也不得超过 8；
- 服务端在同一正确 manifest 下返回坏块时，坏块不得写入主文件或持久化为完成，下一轮只重取该块；
- 非整除块布局中断后，重启必须从已验证块继续；
- 无清单换 URL 时必须丢弃未认证断点；
- 最终文件内容与参考文件一致。

`ManualRedownloadTest` 必须覆盖：其它 marker 缺失仍允许所选 ZIP；三个不同文件可同时登记；同一文件去重；旧 marker 的自身校验不依赖其它文件。

`DownloadConcurrencyTest` 必须证明第九条连接在全局上限处等待，释放许可后继续，峰值不超过 8。

`HotUpdateRoutingTest` 必须钉住动态热更新不读取基础包 manifest、身份查询键稳定，以及“一个成功 + 一个失败”只能显示“部分更新完成”。还必须钉住**首次安装器**同样不给这两包套 manifest，且反向钉住 13 个静态基础包继续走块指纹事务——把判据写宽能让红条消失，代价是整批基础包退回只剩 ZIP 结构预检。

`DiskSpaceTest` 必须钉住 ENOSPC 的各种长相都认得出（含包了两层的 cause 与自环 cause），且超时／分块校验失败／Range 越界这些真正的网络故障**不**被误判为空间不足——反了的代价一样实在：网络故障被当成磁盘满就再也不换线、不重试了。

`ZipPlanTest` 必须用 `ZipOutputStream` 生成**真的 ZIP** 来验（手写字节序列只能证明解析器与作者的想象一致，证明不了它读得懂真实产物），并钉住失败时一律返回 `UNKNOWN`：把残缺数据当成小数字等于把玩家放进去再在解压时翻车，当成大数字则是把装得下的人挡在门外，两头都比「不知道」差。

`UiAssistStateTest` 必须覆盖：显式停留、一次性进入游戏请求与浮层销毁后的状态清零。
`check-download-ui-contract.py` 必须拒绝 decorView 外挂、整屏平移、缺失的横纵滚动容器、教程“否”触发重启，以及缺失的热更新版本复位。


## 03 完工与显示口径（2026-08-13）

- 事务块下载达到 100% 后，客户端会明确显示“正在安装资源 / 解压 x/y”，不再把长时间解压伪装成卡在 100%。
- 完整 ZIP 在 marker 写入前不会被启动流程删除。进程在 03 解压中被杀后，下次启动复用已验证的 1.4GB ZIP，并从 `*.extract.tx` 检查点继续；损坏 ZIP 才清除重下。
- 显示速度只由单调有效进度计算：有 manifest 时是已验证块字节，无 manifest 时是已持久化分段字节。失败块、镜像重试和断点恢复不会重复计入速度；显示使用 3 秒窗口与 EWMA 平滑。
- 普通进度回调只能增加。只有玩家明确触发重下或开始全新任务时才允许归零；镜像切换、块超时和 UI 重绘不能让文件或总进度回撤。
- 下载中的重下（经红色“重试”或调试悬浮窗资源页触发）会中止该文件当前传输、清理该文件断点并从头开始；其它文件继续运行。
